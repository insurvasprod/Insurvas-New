# LA-2 release gates — worked through 2026-09-18

Follows the audit of the same date. That audit's conclusion — **not ready for production, because the
shared database is behind the checkout** — still stands. What changed is that every gate which could
be closed from this environment is closed, the remaining ones are reduced to a single action by
someone with database rights, and one defect was found that would have made the deployment worse
rather than better.

## The one that matters most: the pending migrations would have broken list import

Found while checking the audit's claim that *"the deployed import RPC also has the historical
actor-membership shape defect"*. **The deployed RPC does not have it. Two of the seven pending
migrations did.** The audit had the direction of the risk backwards, and it is the more dangerous
direction.

The sequence, from the repository:

| Migration | Actor check |
|---|---|
| `20260914160000_la_2_2_atomic_lead_import` | `from public.users where id = … and tenant_id = …` |
| `20260914193000_la_2_2_import_actor_membership_fix` | corrected to `tenant_users` — **this is what the live database has** |
| `20260917141000_la_2_2_twenty_thousand_row_batch` | re-emitted the whole function from the 160000 text |
| `20260917146000_la_2_2_imported_leads_reach_the_dialer` | same |

The last two raised the batch cap and added the queue enqueue. To do it they pasted the entire
function body, carrying the pre-fix actor check back with them.

`public.users` has **no `tenant_id` column** — confirmed against `pg_attribute`; membership lives in
`tenant_users`. PL/pgSQL resolves column references when a function runs, not when it is created, so
both migrations would have applied without a single complaint and then raised
`42703 column "tenant_id" does not exist` on **every import**. Applying the bundle would have
introduced the defect that a migration three days earlier existed to remove, and taken list import
down completely — while every local check stayed green.

Both files are fixed to the `tenant_users` shape, matching live.
`lib/agentTemplates/importActorShape.test.mjs` pins it: it checks the **last** migration to define
the function rather than that a fix exists somewhere, because the last one is the only version the
database ends up with. The general-purpose detector in that file is itself run against
`20260914160000` first and fails if it cannot see the known defect — an earlier draft of it matched
nothing at all and passed, which reads as evidence and is worse than failing.

The deployment gate now checks this shape live, so a future paste-over is caught before it ships.

## Gates closed

### `verify:all` could not start — fixed

`scripts/verify-sa6-2.mjs` existed on disk and was registered nowhere, so the orphan check refused to
start the suite — correctly; that check exists because nineteen suites went unrun on this project
across two occasions. Registered as `["SA-6.2 login lockout", "verify-sa6-2.mjs"]`. The suite now
starts and runs.

### The migrations are reduced to one paste — `supabase/deploy/la-2-pending.sql`

Generated by `npm run build:la2-deployment`. Not seven files and a set of instructions, because the
instructions are where the drift came from:

- **One transaction.** Verified first that none of the seven contains `create index concurrently`,
  `vacuum`, or anything else that cannot run inside one. A failure at file five leaves the database
  exactly as it was, rather than five-sevenths migrated — which is the state that produced the
  270-against-327 history gap.
- **It registers itself** in `supabase_migrations.schema_migrations`, in the same transaction as the
  schema it describes, so history and schema move together or not at all.
- **It proves itself before committing.** The tail asserts every relation, function, trigger and
  function-body behaviour the seven files are supposed to produce, and raises with a list if any is
  absent. A bundle that commits is therefore evidence rather than a claim.

That assertion block was run as-is against the live database while writing it. It raised exactly the
expected list, which both validates the block and independently reproduces the audit's gap:

```
LA-2 deployment incomplete: relation tenant_campaign_scrub_rejections; relation
tenant_campaign_costs; relation tenant_vendor_speed_to_lead; function
record_campaign_scrub_rejections; function prevent_internal_dnc_removal; trigger
tenant_do_not_call_permanent; import does not enqueue, so an imported list cannot be dialled;
the import batch cap is still 2000
```

### The schema gap is now a failing check — `npm run verify:la2-deployment`

The audit's real finding was not that code was wrong; it was that a green local suite over a stale
database looked like readiness, and nothing in the repository disagreed. `check:triggers` and
`verify:rpc-contract` each caught one symptom because they happen to enumerate those object classes.
Everything else was invisible.

This gate asserts the whole contract — relations, added columns, functions, triggers, and the two
behaviours that live inside function bodies and cannot be found by enumerating objects. It is
registered in `verify:all`, read-only, and exits non-zero. It currently reports **13 failures**, each
naming the migration that owns it and the consequence.

It is red until the bundle is applied, and that is the point.

### The 100k serving benchmark has a harness — `npm run bench:serve`

LA-2.8 criterion 5, "under 200ms with 100,000 eligible leads", was unrunnable because no fixture and
no harness existed. `scripts/bench-serve-next-lead.mjs` builds one.

Why the criterion matters more than it used to: before LA-2.8 the dialer read
`/api/app/leads?limit=100` and picked the first row, so serving cost was a client-side sort over a
hundred records. `serve_next_lead` put it on a function that scans `lead_queue`, joins `agent_leads`,
resolves six priority tiers and evaluates a calling window per row — on the hot path of every dial.

- Measures the RPC server-side, not over HTTP, so the number can be attributed.
- Reports min / median / **p95** / p99 / max. The criterion is judged on p95, because a mean hides
  the tail and the tail is what an agent experiences.
- Prints `explain (analyze, buffers)` alongside: a pass that rests on a warm cache is not a pass, and
  a sequential scan on `lead_queue` at 100k rows will not survive real data however good the timing
  looks.
- Releases each claim between samples, so every sample faces the same queue depth instead of a
  queue that shrinks by one per iteration.
- The fixture spreads lead states and states-of-residence deliberately. 100k identical fresh leads
  exercise one tier and prove nothing about the tier resolution that makes serving expensive.

**Not run here.** It refuses without `--i-have-a-disposable-project`, and this environment's only
target is the shared project. Inserting six figures of rows and claiming work items on a database
other people are using is not a thing to do quietly — a benchmark that locks a working agent's queue
for fifteen minutes is a denial of service on your own floor.

### Advisor findings — measured rather than repeated

**Mutable function `search_path`.** Reproduced: 614 functions in `public`, 348 with `search_path`
pinned, **266 mutable**. Of those 266, **zero are `SECURITY DEFINER`** and zero reference a
non-public schema.

That reframes the finding rather than dismissing it. The exploit for a mutable search path needs
elevated execution: an attacker creates a shadowing object in a schema that resolves earlier, and the
function runs it with the definer's rights. A `SECURITY INVOKER` function runs with the caller's own
rights, so the same trick grants nothing the caller did not already have. The project's convention
already pins `search_path` on its definer functions, and the catalog agrees. **No migration was
written**, because changing 266 function signatures to fix a warning that carries no privilege
escalation is a large, untestable change for no security gain.

**Duplicate indexes.** Reproduced exactly — **12 sets, 6.4 MB**, matching the advisor's count, by
comparing `pg_get_indexdef` with the index name normalised out. Looser grouping reports unique-versus-
non-unique and partial-versus-full pairs as duplicates, and they are not.

`20260918100000_advisor_duplicate_indexes.sql` drops **three**. All three come from one migration,
`20260911100000_live_runtime_compatibility.sql`, a bridge that created objects `if not exists` to make
a drifted database match its declarations. Each has a canonical partner declared independently and
more than once, so the bridge copy is residue, and each backs no constraint — confirmed against
`pg_constraint.conindid`. The migration checks the canonical partner exists **before** dropping
anything: dropping the copy and leaving a table with no index would turn a maintenance warning into a
sequential scan on the serving path.

| Table | Dropped | Kept |
|---|---|---|
| `agent_leads` | `agent_leads_partner_submission_compat_idx` | `agent_leads_partner_submission_idx` |
| `lead_queue` | `lead_queue_tenant_status_compat_idx` | `lead_queue_tenant_status_queued_idx` |
| `partner_channels` | `partner_channels_direct_compat_idx` | `partner_channels_direct_key_idx` |

**The other nine are left for the database owner, deliberately.** One is disqualifying and the rest
are judgement calls I cannot test:

`public.leads` **cannot** be cleaned up as an index change at all. Both members are load-bearing:

| Index | Role |
|---|---|
| `leads_submission_id_key` | backs `UNIQUE CONSTRAINT leads_submission_id_key` |
| `leads_submission_id_unique_idx` | is the index `FOREIGN KEY verification_sessions_submission_id_fkey` depends on |

Dropping either removes a uniqueness guarantee or breaks a foreign key. That needs a constraint-level
change and a data-integrity decision, not a tidy-up.

The remaining eight, with both members plain indexes and either one droppable:

| Table | Pair | Declared in migrations? |
|---|---|---|
| `lead_queue` | `lead_queue_serving_idx` / `lead_queue_tier_idx` | 1 / 1 |
| `users` | `users_org_idx` / `users_organization_status_idx` | 0 / 0 |
| `subscriptions` | `subscriptions_one_live_per_tenant` / `…_idx` | 4 / 2 |
| `subscription_addons` | `subscription_addons_one_live` / `…_live_idx` | 2 / 1 |
| `organization_addons` | `organization_addons_active_unique` / `…_one_active_idx` | 0 / 0 |
| `outbound_call_attempts` | `…_prospect_idx` / `…_scoring_idx` | 0 / 0 |
| `tenant_call_attempts` | `…_lead_idx` / `…_scorecard_idx` | 1 / 1 |
| `tenant_consent_artefacts` | `…_lead_idx` / `…_tenant_lead_idx` | 1 / 1 |

Three of those tables carry billing state, five pairs are undeclared in any migration — so dropping
one silently changes a live schema that no file describes — and this environment has no rights to
test a drop before it reaches production. Four megabytes does not justify an untested drop on a
subscriptions table.

## Recommendation

Unchanged in conclusion, sharper in shape: **LA-2 is not releasable until the bundle is applied**, and
it is now one paste followed by one command that either goes green or names what is still wrong.

The audit's own framing is worth keeping: a green local suite is necessary and not sufficient. What
was missing was anything that said so out loud. `verify:la2-deployment` now does, and it is wired into
`verify:all`, so the next person to read a green run is reading a claim about the database as well as
the code.

## Second pass — 2026-09-18, later

### A contract failure was handled and then deleted

The companion to the actor-shape defect, and the reason it survived as long as it did. All three
import routes did this:

```ts
const failure = classifyImportFailure(error);
return NextResponse.json({ error: failure.message, code: failure.code }, { status: failure.status });
```

`error` was never logged. So a broken database contract produced:

- for the person importing — *"temporarily unavailable … please try again later"*, a **permanent**
  schema fault described as a transient one, which invites retrying something that will never work;
- for the operator — **nothing at all**. No console line, no stack, no audit row. The cause
  (`column "tenant_id" does not exist`, a missing relation) was classified and discarded in the same
  expression.

`app/api/app/leads/import/route.ts` was worse: it also wrote the failure to
`agent_lead_import_batches.error_message`, storing the **vague user message** in the one durable
record an operator would actually go and read.

A 503 nobody can diagnose is worse than a 500 with a stack trace, because it looks handled.

**Fixed.** `ImportFailure` now carries `cause`. `recordImportFailure(error, context)` classifies and
logs, and all three routes go through it. The batch row stores `failure.cause`. The user-facing
message is unchanged and still gives nothing away — "your database is missing a view" is not
actionable for someone uploading a spreadsheet. The split is the point: the user gets a calm,
honest "nothing was created", and the log gets the truth.

Two things learned while fixing it, both pinned:

- `lib/agentTemplates/errors.ts` **must stay dependency-free**. A first attempt returned a
  `NextResponse` from the helper, which broke `importBatch.test.mjs` instantly — that suite loads the
  module directly under `node --test`, where `next/server` does not resolve. The guard now asserts
  the file imports nothing from `next/`.
- A route must not call `classifyImportFailure` directly, because that is the path that skips the
  record. The guard asserts that too.

Also verified against the live RPC rather than assumed: the function's own refusals come back as bare
codes (`IMPORT_BATCH_INVALID`, `IMPORT_BATCH_SIZE_INVALID`, `IMPORT_ITEM_INVALID`), with no function
name in the message. So the classifier's `import_agent_lead_batch` pattern does **not** catch ordinary
business-rule errors and turn them into "try again later" — a real risk in that regex, which turns out
not to fire. Pinned as a test so it stays that way.

### Board statuses corrected

LA-2.15 and LA-2.16 were still `In progress` on the Notion sprint board despite being retired by
decision 16. Both set to `Cancelled` — an option already in use on that board, so no new value was
invented. The other 22 statuses were left alone: they are the product owner's to move, and this audit
does not have the evidence to promote any of them.

### SA-5.2 checkout had never worked, and the reason was seeded data

`POST /checkout_configurations` answered `404 This Plan was not found` on every attempt.

Not credentials: the Whop sandbox answered `GET /plans` and `GET /products` with 200 for the
configured account. The cause was in `whop_plans`, the table recording "our plan X exists on Whop as
plan Y". It held **six fabricated rows** — `plan_demo_m_0`, `plan_demo_y_0`, … — written by
`scripts/seed-demo-data.mjs`. Verified against the live account: none of the six existed, while its
four real plans were present.

`ensureWhopPlan` returns any stored mapping without asking Whop, deliberately — it saves a round trip
on every checkout. The cost is that a wrong row is believed forever, so the seeder's invented ids meant
the genuine plan was never created and checkout could never open.

Three changes:

- **The seeder no longer touches `whop_plans`.** It is not demo data; it is a record of fact about
  another system, and inventing rows in it does not create a demo, it breaks production checkout. The
  mapping fills itself in on the first real sale, which is what `ensureWhopPlan` is for.
- **A stale mapping now names itself.** Whop's 404 became `CheckoutError` → 409 with the plan, the
  cycle, the offending id and the remedy, instead of an unhandled error → 500 "Could not open
  checkout" with the cause only in a server log nobody was reading.
- **The six rows were removed**, after re-confirming against the live account that none of them
  existed there. `verify:checkout` then passed in full: checkout opens, returns a provider-hosted URL,
  14-day trial, and the real Whop plan was created on first sale exactly as designed.

### SA-5.1 rate limits — the test was stale, the limiter was fine

It asserted "the sixth and seventh are refused with 429" against a hard-coded 5. `SIGNUP_PER_IP.max`
is **10** in the working tree (committed value: 5 — an uncommitted change doubled it), so seven
requests never reached the ceiling and all seven returned 409 from the plan check.

I did not pick a side on a security limit that somebody else is changing. The verifier now **reads
`SIGNUP_PER_IP.max` from source** and sends `max + 2`, so it tests the behaviour — the ceiling engages
and stays closed — at whatever value the rule holds. It passes at 10 and would pass at 5.

> The uncommitted change from 5 to 10 is still worth a decision: it doubles how many accounts one IP
> can attempt per hour, and it arrived with no commit message and no test change.

### SA-4.12 system maintenance — an assertion testing the wrong thing

"future schedule keeps writes available" and "turning maintenance off restores writes" both probed
`POST /api/app/policies` **with no body** and asserted `201`. That route answers 400 from schema
validation for an empty body and always did.

The maintenance gate runs inside `requireFeatureRole`, **before** the body is parsed — which is why the
`read_only` check saw a clean 503. So a validation error is itself proof the request got through the
gate. Both assertions now check "not blocked by maintenance" rather than a payload rule belonging to
another route.

### Screening and dial preflight — a precondition nobody could see

Both prove **fail-closed** screening, which `DEMO_SCREENING_MODE` short-circuits by design. Run against
the shared demo-mode server they failed on assertions that read like compliance defects and were not.
Both now check the flag first and refuse with the exact command to run instead. On a clean server with
the flag off, both pass.

## LA-1.10 transfer inbox latency — fixed, and it was not the inbox

The last unresolved failure from the full `verify:all` run. Reported at 1,154 ms and 1,565 ms against a
1,000 ms budget.

### The inbox query was never the problem

`GET /api/app/inbound` already reads through a single RPC, `list_transfer_inbox_bundle` — one round
trip, no N+1 — over an indexed `(tenant_id, status, queued_at)` scan with `limit 500`.

The first honest measurement was of the environment: **a trivial `select 1` against this database
takes 131 ms.** The database is remote, so every sequential round trip costs more than most queries
do. That reframes the whole problem: latency here is a count of round trips, not a cost of work.

Timed one at a time against the live project, warm:

| Phase | Cost |
|---|---|
| `resolveTenantContext` (membership + user, already parallel) | 219 ms |
| `getMaintenanceStatus` | 183 ms |
| `getEntitlement` | 171 ms |
| `featureKillState` | ~170 ms |
| **preamble total, sequential** | **~740 ms** |
| the inbox RPC itself | 181 ms |

The suite measured 903 ms end to end on a production build. 722 ms of that was `requireFeature`
before the route ran a single line of its own code. The inbox was being blamed for the cost of
authenticating the request.

### The fix

None of those four reads depends on another's result. `tenantId` comes from the session JWT, which is
signed by us and verified before any of them run, so the entitlement and kill-switch reads never
needed to wait for the membership lookup to come back. They now fetch concurrently.

**The decision order is unchanged, and that mattered more than the speed.** Maintenance is still
evaluated before entitlement, so locked mode cannot reveal whether a tenant has a plan; the kill
switch is still evaluated before entitlement, so a paying customer is never told their plan lacks a
feature that is off for everyone. Only the fetching is concurrent — every branch runs in the same
sequence it always did.

Two details worth keeping:

- **An unauthenticated request does no speculative work.** The session is decoded first; with no
  session the function returns the canonical 401 before starting anything. Otherwise a request with
  no credentials would trigger a tenant's entitlement computation, which is a free way to probe.
- **Speculative rejections are captured, not thrown.** If authorisation fails, the caller must see the
  401 or 403 — not an error from a read that only ran early as an optimisation. They are re-thrown
  after the maintenance gate, exactly where they would have surfaced before.

`requireWriteAccess` had the same three-trip shape and got the same treatment. Every write route in
the application goes through it.

### Result

| | Before | After |
|---|---|---|
| Inbox latency (production build) | 903 ms | **527 / 533 / 541 / 573 / 609 / 656 ms** across six runs |
| Headroom against the 1,000 ms budget | 10% | **~45%** |
| Suite result | intermittent — 1,154 ms, 1,565 ms | passes, including the realtime claim broadcast |

The intermittency was the real defect. A check sitting at 90% of its budget fails whenever the network
has a bad minute, and the audit saw exactly that twice.

Regression-pinned in `lib/entitlements/preambleConcurrency.test.mjs`: the four reads must be in one
`Promise.all`, each must appear exactly once (a leftover sequential `await` would silently re-add the
round trip it saves), the three branch comparisons must stay in order, and the unauthenticated path
must still do no work.

### Also fixed on the way

`verify:system` and `verify:switches` read only `NEXT_PUBLIC_APP_URL`, while every other suite takes
`APP_BASE_URL`. They therefore could not be pointed at a clean production server the way the rest can,
and failed with `ECONNREFUSED :3000` whenever the dev server was down. Both now take `APP_BASE_URL`
first and fall back to the old variable, so nothing that relied on it changes.
